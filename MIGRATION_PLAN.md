# План перехода на TS / контракты / shared UI / production-ready

## Текущее состояние (факты, не оценки)

- Клиент: ~87 000 строк, 217 файлов в `client/components`, 29 директорий в `client/scenes` (26 `*.list.js`, 28 `*.edit.js`, 27 `*.create.js`).
- Сервер: ~7 200 строк, 33 контроллера, 38 моделей, 32 файла роутов. Запускается как обычный `node` без транспиляции (TS туда сходу не завезти без отдельного билд-шага).
- Redux: 32 файла `actions/*`, ~162 строковых action-type констант, ни один reducer не типизирован, единого `RootState`/`AppDispatch` нет.
- Тестов нет ни одного (`*.test.js`/`*.spec.js` — 0 файлов), при этом `.gitlab-ci.yml` в стадии `Test` вызывает `yarn test`, а скрипта `test` в `package.json` нет — стадия CI по факту не работает.
- Дублирование компонентов подтверждено grep'ом:
  - `employees.js` (фильтр-селект по сотруднику) скопирован в `shinomontazhs/`, `stos/`, `washs/`, `diskpaintings/`.
  - `updatecutomer.modal.js` скопирован в `shinomontazhs/`, `stos/`, `autoparts/`, `tools/`, `washs/`, `storage/`, `tyres/` (7 копий).
  - 12 файлов `*.row.js` / `*.row.boss.js` — у каждого свой ручной "мобильный" layout таблицы (тот же паттерн, что был у Employees до миграции).
- Уже сделано (страница Employees, эта сессия): апгрейд Tailwind 1→3 с сохранением визуала, основа shadcn/ui (`client/components/ui`), TS-инфраструктура (babel уже поддерживал TS, добавлен `@typescript-eslint`, починен `.prettierrc`), страница `Employees.list.tsx` + `employee.tsx` переведены на TS/shadcn/пагинацию/скролл вместо мобильного layout.
- Решено и сделано (эта сессия, после вашего ответа "1. транспиляция 2. генерация"):
  - **Сервер транспилируется.** `start.js` уже вызывал `@babel/register()` (тот же babel, что и у клиента, с `@babel/preset-typescript`) — просто не хватало `.ts`/`.tsx` в списке расширений. Добавил `extensions` в `start.js` и `"ext": "js,ts,json"` в `nodemonConfig` — сервер теперь может require'ить `.ts`-файлы наравне с `.js`, без Docker/`tsc`-билд-шага. Проверено живым запуском (`node start.js`, подключение к Mongo, HTTP отвечает).
  - **Контракты теперь генерируются, а не пишутся руками.** `scripts/generate-types.js` require'ит каждый `server/model/*.js`, читает **скомпилированную** Mongoose-схему (`Model.schema.paths` — не статический парсинг, а то, что Mongoose реально знает о полях: тип, `required`, `enum`, поля от плагинов типа `mongoose-sequence`, `_id`/`__v`) и пишет `.ts`-интерфейс на каждую модель. Запущен на все 38 моделей → `common/types/generated/*.ts`. Подключено к `yarn typecheck` (сначала генерирует, потом `tsc --noEmit`), так что типы не могут молча устареть при локальной проверке.
  - Обнаружил, что в репо уже есть закреплённая договорённость про общий код клиент/сервер — директория `common/` (сейчас там `common/enums/task-statuses.js` и `common/enums/shinomontazh-statuses.js`, уже импортируются и из `server/model/*`, и из `client/components/*` обычными относительными путями, без алиасов). Контракты положил туда же (`common/types/generated/`, `common/types/api.ts`), а не в новую `shared/`, чтобы не плодить второй параллельный "общий" каталог.
  - `client/types/{employee,place}.ts` (ручные версии) удалены, `Employees.list.tsx`/`employee.tsx` теперь импортируют `IEmployee`/`IPlace` из `common/types/generated/`.
  - Что генератор **не может** вывести сам: 34 поля в 12 моделях — это `type: Array` без указания типа элемента (сам Mongoose тоже не знает, чем их наполняют) — стали `unknown[]`. Для `Employee.role`/`Employee.address` явно знаю из использования, что это `string[]` — задал через `OVERRIDES` в скрипте. Остальные 34 поля можно уточнять так же по мере миграции соответствующих страниц.

## Принципы

1. **Без big-bang переписывания.** Это боевая CRM, заморозить её нельзя. Миграция — постранично, как Employees.
2. **Каждая тронутая страница мигрирует полностью за один заход**: TS + контракты + вынос дублирующихся компонентов в shared/ui + enum вместо констант + отказ от мобильного layout таблиц. Не растягивать на отдельные "заходы по всему приложению".
3. **Инфраструктура — один раз, глобально**; конкретные страницы — по мере необходимости.
4. **Правило двух**: если паттерн скопирован во второй раз — выносим в shared, не в третий.

## Фаза 1 — TypeScript

- Клиент уже разблокирован (babel, webpack, eslint, prettier настроены в этой сессии). Стратегия: конвертировать файл при его правке, без принудительной массовой конвертации.
- `tsconfig.json`: сейчас `strict: false`, `checkJs: false`. Дорожная карта — не включать `strict` целиком сразу (нереалистично для 87k строк), а по мере того как директория полностью переходит на `.ts/.tsx`, добавлять точечный `overrides`-профиль с `noImplicitAny` для неё.
- Redux: типизировать `actions`/`reducers` по мере миграции их потребителей (как в Employees.list.tsx — типизируется только используемый срез стора, не весь `RootState`). Собрать общий `RootState`/`AppDispatch` — отдельная задача после того как критическая масса reducer'ов типизирована.
- Сервер: **решено — транспиляция** (см. "Уже сделано" выше). `start.js` через `@babel/register` теперь понимает `.ts`/`.tsx` наравне с `.js`, без отдельного `tsc`-билда и без изменений в Docker (тот же `yarn start` → `node start.js`). Дальше — конвертировать `server/*.js` в `.ts` по мере правки конкретных контроллеров/моделей, как и клиент.

## Фаза 2 — Контракты фронт/бек

- **Решено и сделано — генерация.** `scripts/generate-types.js` → `common/types/generated/*.ts`, все 38 моделей, подключено к `yarn typecheck` (см. "Уже сделано" выше). `IApiResponse<T>` лежит рядом в `common/types/api.ts` (не генерируется — это не схема модели, а обёртка ответа контроллеров).
- Осталось по ходу миграции страниц:
  - Использовать сгенерированные `common/types/generated/I<Model>` вместо `any` в компонентах/reducers по мере их перевода на TS (уже сделано для Employee/Place).
  - Отдельные *payload*-типы для create/update (когда форма отправляет не весь документ, а подмножество полей) — писать руками рядом с генерируемыми, генератор их не выводит.
  - Уточнять `OVERRIDES` в `scripts/generate-types.js` для оставшихся 34 `unknown[]`-полей по мере миграции их страниц (Autoparts, Cond, Diskpainting, Shinomontazh, Sto, Storage, Tools, Tyres, Wash, Window).
  - Завести типизированный `apiFetch<T>(url): Promise<IApiResponse<T>>` вместо ручных `fetch(...).then(r => r.json())` в каждом `redux/reducers/*.js`.
  - Долгосрочно можно рассмотреть переход на zod/io-ts как единственный источник правды (схема одновременно валидирует запросы на сервере и генерирует типы), но это отдельное решение поверх уже работающей генерации — пока не требуется.

Перевести в `.ts` с `enum` или `as const`-объединением строк, чтобы места использования получили автодополнение и проверку исчерпаемости (`switch` по статусу).

## Фаза 5 — Production readiness

- **Тесты**: `jest`/`@testing-library/react` уже в devDependencies, но не используются и нет скрипта `test` в `package.json` — CI-стадия `Test` в `.gitlab-ci.yml` сейчас нерабочая. Завести скрипт и первые тесты — начать с `components/ui/*` (дёшево, высокая ценность) и критичных сценариев (аутентификация, создание заказа).
- **CI**: добавить `lint` + `typecheck` + `build` как обязательные шаги перед `Build&Run`/деплоем — сейчас в пайплайне их нет вообще.
- **Размер бандла**: `js/main.bundle.js` — 2.66 MiB, сам webpack предупреждает об этом. Ввести код-сплиттинг по роутам (`React.lazy`/`Suspense`, react-router v5 это поддерживает) — самое дешёвое улучшение без изменения поведения.
- **Обработка ошибок**: error boundary на верхнем уровне React-дерева не найден — добавить, плюс аудит обработки ошибок на сервере.
- **Секреты**: в `.env` лежит `MONGO_URL` с логином/паролем — стоит проверить, не закоммичен ли этот файл в историю, и вынести секреты из репозитория (это отдельное решение, не буду делать втихую).

## Фаза 6 — Порядок страниц

Продолжать по одной странице, как Employees. Следующие кандидаты — по эффекту консолидации:
