# Project rules

## UI components: use shadcn/ui

New or redesigned screens MUST be built with **shadcn/ui** components, not raw HTML controls or ad-hoc Tailwind markup.

- Reusable primitives live in `client/components/ui/*` (`Button`, `Input`, `Select`, `Checkbox`, `Card`, `Dialog`, `AlertDialog`, `Table`, `Pagination`, `Badge`, `BadgeList`, `Label`, `Combobox`, `Accordion`, `Tabs`, `Field`/`FieldGroup`/`FieldSet`/`FieldLabel`/`FieldDescription`/`FieldError`/`FieldSeparator`, `Separator`, etc.). Use these instead of `<button>`, `<input>`, `<select>`, plain `<table>`, etc.
- If a needed primitive doesn't exist yet, add it to `client/components/ui/` following the same pattern (Radix primitive where applicable, `cn()` from `client/lib/utils` for class merging, `React.forwardRef`) rather than writing one-off styled elements inline. When unsure what a primitive's real shadcn markup/API looks like, fetch the actual docs (e.g. `https://ui.shadcn.com/docs/components/<name>` or the registry JSON at `https://ui.shadcn.com/r/styles/new-york/<name>.json`) rather than guessing - don't invent ad-hoc "boxed card" styling for things shadcn already has a documented pattern for.
- Styling follows the shadcn design tokens defined in `client/assets/scss/main.scss` (`--background`, `--card`, `--muted`, `--border`, etc.) via the `bg-*`/`text-*`/`border-*` Tailwind classes those components already use - don't hardcode hex colors for these components.
- **Complex/long forms**: follow shadcn's own `Field` family (`client/components/ui/field.tsx`) for structure - `FieldGroup` > `Field` (+ `FieldLabel`, `FieldDescription`, `FieldError`) rather than one `<Label>`/`<Input>` pair per hand-rolled `<div className="grid gap-2">`. Validation: put `aria-invalid`/`data-invalid` on the input/`Field`, message in `<FieldError>` - the `Input` component already has `aria-invalid:border-destructive` styling built in (and `tailwind.config.js` registers the `aria-invalid` variant under `theme.extend.aria`, since it isn't one of Tailwind's built-in ARIA state variants).
- **Checkboxes** (including checkbox grids like a role/permission picker): use the bordered "card" pattern - `<FieldLabel htmlFor={id}><Field orientation="horizontal"><Checkbox id={id} .../><FieldContent><FieldTitle>Label text</FieldTitle><FieldDescription>optional</FieldDescription></FieldContent></Field></FieldLabel>`. The outer `FieldLabel` is the real `<label>` (click anywhere in the card toggles the checkbox) and gets its border/`bg-primary/5` tint from `has-[>[data-slot=field]]`/`has-data-[state=checked]` selectors already baked into `FieldLabel` - don't wrap a `FieldLabel` inside another `FieldLabel`, use `FieldTitle` (not `FieldLabel`) for the inner text since it renders a `<div>`, not a nested `<label>`.
- **Collapsible groups of fields** (a long form split into named sections, only one open by default): use `Accordion`/`AccordionItem`/`AccordionTrigger`/`AccordionContent` (`type="multiple"`), not a custom chevron-button-plus-`Card` component - that was an earlier ad-hoc `CollapsibleCard` attempt that's since been replaced everywhere in favor of the real shadcn `Accordion`.
- **Lists of colored badges with an optional "show all" toggle** (e.g. an employee's positions, an account's access roles): use `BadgeList` (`client/components/ui/badge-list.tsx`) - `<BadgeList values={role} labels={ROLE_NAMES} colors={ROLE_COLORS} />` (pass `limit={Infinity}` for an uncapped preview, e.g. inside a form; the default `limit={5}` plus a "Показать все (N)" toggle is for table cells). Colors are defined *alongside* the list they belong to (e.g. `client/lists/role-list.js`, `client/lists/account-role-list.js` each export `{ name, value, color }` entries) rather than in a separate derived-by-index consts file - so a new item always ships with its own color and there's one shape both employees' and accounts' role lists share.
- **A form with mutually-exclusive modes within the same create flow** (e.g. "add one" vs. "bulk import"): use `Tabs`/`TabsList`/`TabsTrigger`/`TabsContent` inside the `Dialog`, not two separate routes/pages - see `client/scenes/Materials/Materials.list.tsx` (single material vs. Excel import).
- Reference implementations of this pattern: `client/scenes/Employees/Employees.list.tsx` (list screen: search + sortable table + pagination + create/edit in a `Dialog`) and `client/components/places/place.form.tsx` / `client/components/employees/employee.form.tsx` / `client/components/accounts/account.form.tsx` / `client/components/materials/material.form.tsx` (complex forms: `Accordion` sections, each containing `FieldGroup`/`Field`, checkbox cards, and `BadgeList` previews). New list screens should follow the Employees/Places/Accounts/Materials list structure; new complex forms should follow the same form structure.

This project has no `components.json` / shadcn CLI setup - primitives were added by hand under `client/components/ui/`. Keep new ones consistent with the existing ones instead of running the CLI.

## Roles, typed constants, and access control

- **Typed constants over bare strings.** For a fixed set of values (roles, statuses, types) prefer a typed TypeScript source of truth - a `const ... as const` object/array with a derived union type, or a TS `enum` - instead of untyped string literals passed around and compared ad hoc. This lets `tsc` catch typos and rename mistakes that a plain `.includes('admin')` scattered across dozens of files can't. When a value is also a stored DB string (e.g. `role-list.js`/`account-role-list.js` entries, where `value` must match existing persisted data), keep the constant's value identical to what's already stored - the goal is compile-time typing on top of the existing values, not a data migration.
- **Give roles readable helper methods.** Don't repeat raw role-string checks (`auth.roles.includes('bookkeeper')`, `role.indexOf('admin') !== -1`, etc.) inline at every call site - the codebase currently has 200+ of these. Add small named helpers (e.g. `isAdmin(roles)`, `isBookkeeper(roles)`, `hasRole(roles, Role.Admin)`) in one shared place instead, so intent is readable at the call site and the set of valid roles/logic has a single source of truth to update. This applies even to a check that looks trivial enough to inline: `client/scenes/Vendors/Vendors.list.tsx`, `Organizations/Organizations.list.tsx`, and `Categorys/Categorys.list.tsx` each independently declare the exact same `const isBossOrAdmin = (roles: string[]) => roles.includes('boss') || roles.includes('admin')` - that's the "one shared place" rule already being missed in practice; new/redesigned screens needing this should import a shared helper (e.g. from a new `client/lib/roles.ts`) instead of adding a fourth copy, and these three should move onto it opportunistically when next touched.
- **Enforce roles on the server, not just the frontend.** Hiding a button, a `Sidebar` link, or a page behind a frontend role check (`!auth.roles.includes(...)`) is UX only - it does not stop a direct API call. Every protected `server/controller/*.js` handler / `server/routes/api/*.js` route that performs a privileged read or write must independently check the authenticated user's role (via the existing JWT/passport auth in `server/server.js`, which already decodes `role` off the `User`/account record) before proceeding, not rely on the client to have hidden the option.

## Layout: mobile-first

Build markup mobile-first, not desktop-first-with-a-mobile-patch.

- Unprefixed Tailwind classes are the **base/mobile** styles; layer larger layouts on top with min-width breakpoint prefixes (`sm:`, `md:`, `lg:`, `xl:`, `2xl:` - Tailwind's defaults, unmodified in `tailwind.config.js`: 640/768/1024/1280/1536px). Don't reach for `max-*` variants to carve out a mobile view from desktop-first markup.
- Default to a single-column/stacked layout, then switch to multi-column/row at `sm:`/`md:` and up (e.g. `flex flex-col sm:flex-row`, `grid grid-cols-1 sm:grid-cols-2`) - this is already the pattern in the redesigned screens' filter bars and form grids (`client/scenes/Materials/Materials.list.tsx`, `client/scenes/Sto.prices/Sto.prices.list.tsx`, the `*.form.tsx` files).
- Tables that don't fit narrow screens get `overflow-x-auto` on their wrapper rather than being hidden or redesigned per-breakpoint - see the same list screens' table wrappers.
- Keep tap targets and spacing usable at phone width when adding new interactive elements (buttons, table row actions, dropdown items) - don't rely on hover-only affordances.

## Architecture direction: Feature-Based

The current codebase is organized **by technical layer**, not by feature - top-level `client/scenes/`, `client/components/`, `client/redux/reducers/`, `client/redux/actions/`, `client/lists/` each hold files for every domain side by side (an employee's scene, component, reducer, and list all live in different top-level folders). That's the existing structure; it is **not** being described as feature-based here.

Going forward, **new features should move toward Feature-Based organization**: colocate a feature's scene/screen, its components, its state (reducer/actions), and its supporting lists/types under one feature-scoped location, instead of adding another file to each of the parallel `scenes/`/`components/`/`redux/` trees. Concretely:

- When starting a genuinely new feature (not a redesign of an existing screen in place), prefer grouping its files together rather than splitting them across the legacy top-level folders.
- When redesigning an existing screen (the current, most common kind of task here - see the shadcn/ui rules above), it's fine to keep following the established location convention (`client/scenes/<Feature>/<Feature>.list.tsx`, `client/components/<feature>/*`, `client/redux/reducers/<feature>.js`) rather than migrating it - don't do a drive-by restructuring of a screen's file locations as part of an unrelated redesign or bugfix.
- This is a direction to move in, not a claim about the current layout - don't describe the existing `scenes/components/redux` split as already feature-based in comments, docs, or explanations.

## Shared functionality over per-domain copies

This repo has ~15 structurally similar "order/work-ticket" domains (`client/components/<domain>/*` + `client/scenes/<Domain>/*` for shinomontazhs, stos, washs, windows, conds, tyres, autoparts, tools, storage, diskpaintings, etc.). They currently duplicate the same interactions and visuals by copy-paste across domains rather than sharing one implementation. When you touch one of these and notice the same problem already solved elsewhere, extract a shared component/hook instead of pasting a new copy - don't let the count grow.

- **Customer search-or-create.** `client/components/shinomontazhs/shinomontazhs.work.create.js`, `stos/stos.work.create.js`, `washs/washs.work.create.js`, `tyres/tyres.preorder.create.js`, and `storage/storage.preorder.create.js` each reimplement the same flow: fetch candidate matches from `GET /api/v1/customerfind/:regnumber/:vinnumber/:phone`, keep parallel `customer`/`activeCustomer`/`customerList` state, and an `applyCustomer`/`checkCustomer` pair that copies fields onto local state and decides create-vs-patch on submit - only a handful of domain-specific fields differ (`kuzov`/`diametr` for shino, `washCategory`/`washClass` for wash, etc.). The next domain that needs this should get a shared `useCustomerPicker` hook or `<CustomerPicker>` component, not a sixth copy - and existing ones should move onto it opportunistically when you're already in the file for another reason (not as a drive-by rewrite otherwise).
- **Place/address (точка) picking.** `tools/tools.preorder.create.js`, `autoparts/autoparts.preorder.create.js`, `storage/storage.preorder.create.js`, and `tyres/tyres.preorder.create.js` each render their own `<select>` over `s.places.list` with an identical "Выберите место" placeholder and `it.id`/`it.name` mapping; `shinomontazhs`/`stos`/`washs` instead derive a `currentPlace` from `auth.place` inline. `client/components/shared/filters/PlaceFilter.js` already extracts this for list-page *filtering* - do the same for the create/edit *form-field* variant instead of pasting another `<select>`.
- **Status color-coding.** `shinomontazhs/shinomontazhs.row.js`, `stos/stos.row.js`, `washs/washs.row.js`, and `storage/storage.row.js` each hardcode the same `taskStatuses[n] -> Tailwind bg-color` mapping inline via `cx()`. This belongs in one shared status-color helper or `StatusBadge` component, not a per-domain switch.
- More generally, this isn't limited to customers/places: before adding a new filter bar, badge, empty-state message, or similar UI/logic piece, check whether an existing domain already solved the same problem and reuse or extract rather than re-implementing it inline.

## Navigation: back must restore the list you came from

Drilling into a row (a detail/view page, a sub-form) and then returning - via a browser back button *or* an in-app "back"/"К списку" control - must land back on the exact same filtered/sorted/paginated state of the list, not a reset one. This matters most for a list whose detail view is a separate route (so the list component unmounts and loses its in-memory state), but the same expectation applies to any list→detail flow.

- Keep the list's filters/search/page/page-size in the URL (query params), not only in component state - state that lives only in memory disappears the moment the list unmounts. Restore it from `location.search` on mount (a lazy `useState` initializer), and push filter/page changes back into the URL as they happen (`history.replace`, so typing doesn't spam browser history) so the address bar always reflects the current view.
- Make an in-app "back" control (e.g. a view page's "К списку X" button) call `history.goBack()` instead of `<Link to="/x/list">` - a hardcoded destination can't reproduce whatever filtered/paginated URL the list was actually showing before the user drilled in, but `goBack()` always lands exactly where they left off, same as the physical browser back button.
- Reference implementation: `client/scenes/Customers/Customers.list.tsx` (URL-synced filters/page via `buildListSearch`, restored via a lazy `useState` initializer reading `location.search`) and `client/scenes/Customers/Customers.view.tsx` (its "К списку клиентов" button calls `history.goBack()`). Watch for the same trap that fix hit: if a list component is reused across multiple routes (e.g. a list route plus create/edit routes rendering the same component so a dialog can overlay it), guard the URL-sync effect so it doesn't fire while on those other routes - otherwise it clobbers the create/edit URL and closes the dialog it's supposed to leave alone.

## Dates: use moment

For new date handling (parsing, formatting, comparing, arithmetic), use **`moment`** - it's a direct dependency (see `package.json`).

- `dayjs` is also present but only used in one legacy file (`client/scenes/Report/shinomontazh/SalaryCell.js`) - don't add new `dayjs` usages, prefer `moment` for anything new.
- `client/lib/legacy-date.ts` (`parseLegacyDate`/`formatLegacyDate`) is a special case, not a general-purpose date util: it exists specifically to correctly parse the non-ISO `DD.MM.YYYY HH:mm` strings several Mongoose schemas store in a `date` field (see the comment at the top of that file for why `new Date(raw)` is unsafe there). Keep using it for those pre-existing `date` fields; reach for `moment` for everything else.
